# 2026-09-23: `cujson` CLI

## Current State
- `cujson-cli` crate builds a `cujson` binary with subcommands `info`, `parse`, `tape`, `verify`, `bench` (`crates/cujson-cli/src/main.rs`), on top of the public `cujson` API only (`parse`/`parse_lines`/`parse_file`/`cuda_info`, `cujson::cpu::parse`, `cujson::tape::diff_tapes`) — no tape-comparison logic reimplemented in the CLI.
- The crate always enables `cujson`'s `cpu-reference` and `serde` features (`crates/cujson-cli/Cargo.toml`); its own `cuda` feature forwards to `cujson/cuda`.
- `cujson verify [FILE] [--lines] [--chunk-bytes N]` (`crates/cujson-cli/src/verify.rs`) prints `cuda_info()` output first, then per-input PASS/FAIL lines for GPU parse, tape-vs-CPU-reference (`diff_tapes`), and `to_value()`-vs-`serde_json` (per line in lines mode), the first mismatch's `Display` text on FAIL, and a final `N/M checks passed` line. With no `FILE` it runs three fixture checks: standard mode over `tests/fixtures/twitter_sample_large_record.json` (`include_bytes!`), and lines mode over `tests/fixtures/twitter_sample_small_records.json` once with `chunk_bytes=0` (one chunk) and once with `chunk_bytes=4096` (forces several chunks).
- Exit codes, uniform across `info` and `verify`: `0` all PASS, `1` any FAIL or other error, `2` CUDA unavailable — not compiled in (`cujson::Error::CudaNotCompiled`), no driver/runtime (`cujson::Error::Cuda{..}`), or no device (`cujson::Error::NoDevice`) — implemented by `CliError::NoCuda` (`main.rs:102-125`) for `info`/`parse`/`tape`/`bench`, and directly in `verify::run` (`verify.rs:40-113`) since it needs the info block printed before deciding the exit code.
- `cujson parse FILE [--lines] [--chunk-mb N] [--pointer P]... [--time] [--repeat N]` prints a one-line summary (bytes, tape length via `Tape::len()`, `Document::depth()`) with no `--pointer`, else each pointer's `to_value()`; `--time` reports min/median over `--repeat` runs excluding the first when `repeat > 1` (`main.rs:200-209`).
- `cujson tape FILE [--lines] [--cpu]` writes TSV `idx\toffset\tchar\tpair` reading `Tape::structural`/`Tape::pair_pos` directly (`main.rs:213-242`); `--cpu` routes through `cujson::cpu::parse`, so this subcommand works in a CUDA-less build.
- `cujson bench FILE [--repeat N]` times `cujson::parse` (labelled "includes H2D copy") against `serde_json::from_slice::<Value>`; `simd-json` is an optional feature (`crates/cujson-cli/Cargo.toml`) — with it, times `simd_json::to_owned_value` too, without it prints "not built (enable with --features simd-json)" instead of an error.
- Repo-root `.cargo/config.toml` (new) contains only `[alias] gpu-verify = "run --release -p cujson-cli --features cuda -- verify"`; `cargo gpu-verify --help` resolves and runs `cujson verify --help` (confirmed in this container, no GPU).
- `crates/cujson-cli/tests/cli.rs`: `assert_cmd` tests for argument errors (`no_subcommand_is_an_argument_error`, `parse_missing_file_argument_is_an_error`, `tape_missing_file_is_an_error`, `tape_nonexistent_file_is_an_error`), `tape --cpu` output shape on a 7-byte tiny input in both standard and `--lines` modes, and no-CUDA/no-driver behaviour split by `#[cfg(feature = "cuda")]` vs not, each asserting the specific exit code (2). Two tests requiring a real GPU are `#[ignore = "requires GPU"]`.
- `ldd target/release/cujson` (release build, `--features cuda`, default `CUJSON_CUDA_ARCHS`) lists only `libstdc++.so.6`, `libgcc_s.so.1`, `libc.so.6`, `libm.so.6`, and the dynamic linker — no `libcudart`/`libcuda` entry, matching the crate doc comment's claim (`crates/cujson/src/lib.rs:16-18`) that linking `cudart_static` leaves only the driver (`libcuda.so.1`, dlopen'd at runtime) as a CUDA dependency. This is tier 3 / unverified for the driver-load path itself — this container has no `libcuda.so.1` and no GPU, so `cuda_info`/`parse`/`verify` were only exercised through their no-driver error path here (`CUDA error 35`, i.e. `cudaErrorInsufficientDriver`/similar), never against a real device.
- Feature combinations run: `cujson-cli` alone with no features and with `--features cuda` (`cargo build`/`cargo test`/`cargo clippy --all-targets -- -D warnings`, all clean); workspace-wide `cargo clippy --workspace --all-targets -- -D warnings` and again with `--features cujson-cli/cuda`; workspace-wide `cargo test --workspace` and again with `--features cujson-cli/cuda`. All four combinations pass with zero warnings/failures (ignoring the GPU-only tests, which are marked `#[ignore]`).

## Missing
- `simd-json` bench path is untested beyond "builds and links" — no run compares its numbers against cuJSON/serde_json here (no fixture-scale timing done in this container, and the GPU path can't run at all).
- `cujson verify`'s per-line lines-mode check assumes `Document::lines()` and a `str::lines()` split over the same input agree on which lines are blank/skippable; not fuzzed here beyond the two bundled fixtures.

## Divergence
- `docs/plan/07-cli.md` writes `--chunk-mb N` for `parse` but `--chunk-bytes N` for `verify`; the CLI keeps that inconsistency as specified (`parse`'s flag is in MB, `verify`'s in bytes) rather than unifying them, since the brief's `07-cli.md` acceptance section and this task's own instructions both spell `verify`'s flag as `--chunk-bytes`.
- The brief's exit-code note ("clear message ... e.g. 2") is implemented as exactly 2 for `CudaNotCompiled`, `NoDevice`, and `Cuda{..}` (driver/runtime failures) alike, since a driverless container's `cudaGetDeviceCount` failure (`CUDA error 35`) is indistinguishable in practice from "no device" from the CLI's point of view, and the brief groups "CUDA isn't compiled in or no device/driver exists" as one case.

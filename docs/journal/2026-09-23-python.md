# 2026-09-23: Python bindings (task 08)

## Current State

- `crates/cujson-py/Cargo.toml`: `cdylib` crate named `cujson` (`[lib] name
  = "cujson"`, `crate-type = ["cdylib"]`), `publish = false`, feature `cuda
  = ["cujson/cuda"]`, `pyo3 = { workspace = true, features =
  ["abi3-py310", "extension-module"] }` — `pyo3 = "0.29"` pinned in the
  root `Cargo.toml`'s `[workspace.dependencies]`, resolved to `0.29.2`,
  which has `Python::detach` (0.29's rename of `allow_threads`) and
  `pyo3::sync::PyOnceLock` (`GILOnceCell` is now `pub(crate)`-only in this
  version)
- `crates/cujson-py/pyproject.toml`: `name = "cujson"` (task 09's release
  workflow seds this to `cujson-cu12`/`cujson-cu13`), `module-name =
  "cujson._cujson"`, `python-source = "python"`,
  `python/cujson/{__init__.py,__init__.pyi,py.typed}`. The built wheel's
  extension lands at `cujson/_cujson.abi3.so` inside the `cujson` package
  dir, confirmed by unzipping `/tmp/dist-cuda/*.whl` in this session
- `crates/cujson-py/src/lib.rs`: `#[pymodule] fn _cujson` registers
  `Document`, `parse`, `parse_file`, `parse_lines`, `cuda_info` after
  `exceptions::init`. `extract_bytes` (`lib.rs:20-35`) accepts `str`
  (UTF-8-encodes it), `bytes`, `bytearray` via direct downcasts, and falls
  back to `bytes(obj)` (a Python-level call) for `memoryview` and any other
  buffer-protocol object — `pyo3::buffer::PyBuffer` is gated on `not
  Py_LIMITED_API` (`pyo3-0.29.2/src/buffer.rs:3`), unavailable under this
  crate's `abi3-py310` limited-API build unless the interpreter reports
  `Py_3_11`, so the wheel's `bytes(obj)` fallback works uniformly instead
- `Document` (`lib.rs:38`) is `#[pyclass(frozen)]` wrapping
  `cujson::Document<'static>`, built only from `parse_owned`/
  `parse_file`/`parse_lines_owned` — never borrows a Python buffer past the
  call that built it. `Document` methods (`to_python`, `pointer`, `lines`,
  `__len__`, `__iter__`) convert straight to Python objects rather than
  exposing a `Node` wrapper type, so no self-referential
  Document/Node-lifetime struct is needed on the Python side
- `crates/cujson-py/src/convert.rs`: `node_to_object` walks
  `cujson::tape::Node` directly into `Py<PyAny>` (dict/list/str/int/
  float/bool/None) without building a `serde_json::Value` first — the
  "preferred, direct" path named in the brief. `number_to_object`
  (`convert.rs:45-61`) mirrors `Node::to_value`'s int-vs-float split
  (`crates/cujson/src/tape/document.rs`'s `to_value`, `serde` feature) so
  both conversion paths pick the same Python type for a given number
  literal — not verified by an automated parity test this task (see
  Missing)
- `crates/cujson-py/src/exceptions.rs`: builds the hierarchy with Python's
  own `type()` builtin (`make_type`, `exceptions.rs:17-27`) rather than
  `pyo3::create_exception!`, which only supports one base class —
  `CujsonError(Exception)`; `InvalidUtf8Error`/`UnbalancedError`/
  `InputError` `(CujsonError, ValueError)`; `CudaError(CujsonError,
  RuntimeError)`; `CudaNotCompiledError`/`NoDeviceError(CudaError)`. Each
  class is cached in a `pyo3::sync::PyOnceLock<Py<PyType>>` static, set
  once in `exceptions::init` (called from `#[pymodule] fn _cujson`) and
  read by `to_pyerr`/`to_pyerr_tape` on every error path — `err_from`
  (`exceptions.rs:89-95`) panics if called before `init`, which is
  unreachable from Python since `init` runs first inside the module
  constructor
- `to_pyerr` (`exceptions.rs:100-131`) maps every `cujson::Error` variant;
  `CudaNotCompiled`'s message names both wheels literally: "install a GPU
  wheel (`pip install cujson-cu12` or `pip install cujson-cu13`, matching
  your CUDA major version)" — asserted by
  `crates/cujson-py/tests/test_api.py::test_parse_without_cuda_raises_helpful_error`
  checking both substrings are present
- `crates/cujson/src/lib.rs` gained `parse_lines_owned(input: Vec<u8>,
  opts: LinesOptions) -> Result<Document<'static>, Error>`
  (`lib.rs:164-179`), the owned counterpart to `parse_lines` that
  `parse_owned` already had relative to `parse` — needed so
  `cujson.parse_lines()` on the Python side can return a `Document` that
  owns its bytes instead of borrowing a Python buffer past the call. A
  no-cuda unit test (`tests_no_cuda::parse_lines_owned_without_cuda_feature_errors`,
  `lib.rs`) covers the same graceful-error path the sibling functions have
- `crates/cujson-py/tests/test_api.py`: non-GPU tests (`test_import`,
  `test_exception_hierarchy`, `test_cuda_info_reports_a_dict`,
  `test_cuda_info_not_compiled_reports_false`,
  `test_parse_without_cuda_raises_helpful_error`) run against whichever
  wheel is installed and skip the CUDA-specific assertion when
  `cuda_info()["compiled"]` is `True`. Four `@pytest.mark.gpu`-equivalent
  tests (gated by `CUJSON_TEST_GPU=1` via a local `skip_no_gpu` mark
  rather than a registered pytest marker — see Divergence) compare
  `cujson.parse`/`parse_lines`/`parse_file`/`pointer` against
  `json.loads` on `tests/fixtures/twitter_sample_{large_record,
  small_records}.json`

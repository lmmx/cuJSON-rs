- The tape of that file has 10,355,007 entries: 113,120 objects, 31,203 arrays, 5,088,241 keys (14.95 MB), 4,963,380 strings (99.9 MB, of which 2,843,045 contain a backslash escape, the sampled ones being non-ASCII text written as `\uXXXX`), 14,348 integers and 289 floats
- The tape occupies 79 MiB (`structural` plus `pair_pos`, 8 bytes per entry), 0.35 times the input size

### Subcommands and options

- `run` times engines at two levels per engine (`parse`: parse and discard; `walk`: parse then visit every node) and prints median, minimum and maximum wall time over `--reps` (default 5) after `--warmup` (default 2), GB/s, rows/s, per-phase medians and peak RSS above the loaded corpus (`/proc/self/status` `VmHWM`, reset through `/proc/self/clear_refs`); `--json` prints one object per engine and level
- When both `simd-par` and `cujson-pipe` ran at the `walk` level, `run` ends with `overall (walk, whole file): simd-par Xs, cujson-pipe Ys: cujson-pipe is Z.ZZx faster` (or `slower`), and with `--json` one more object with `simd_par_s`, `cujson_pipe_s`, `speedup` and `tape`; `--tape cpu` adds a note that the tape was built on the CPU
- `run --batch-mb N` groups rows into JSON Lines batches of at most N MiB (default 256; cuJSON rejects inputs of 2 GiB or more); batches are built before timing
- `run --tape gpu|cpu` selects the tape source of the `cujson-*` engines: `cujson::parse_lines`, or the sequential reference builder `cujson::cpu::parse`, which lets the tape walk be timed without a GPU
- `run --pinned-input` copies each batch once, before timing, into a `cujson::PinnedBuffer` and the `cujson-*` engines parse from it
- `run --gpu-threads N` sets the number of threads parsing on the GPU at once in `cujson-pipe` (default 1) and calls `cujson::set_max_concurrent_parses(N)` for the duration
- `run --threads N` sets the rayon thread count (default: all cores, 20 on the development machine)
- `verify` compares per-row checksums of simd-json, `cujson::cpu::parse(.., Mode::Lines)` and, when a device is present, `cujson::parse_lines`, and exits non-zero on any mismatch
- `leak` parses the first batch `--iters` times (default 30) with `--engine` and prints VmRSS, VmHWM and free device memory (`cujson::device_memory`) after each iteration

### Engines

- `simd`, `simd-par`, `simd-buf`, `simd-buf-par` call `simd_json::to_borrowed_value` (or `to_borrowed_value_with_buffers` for the `buf` variants) per row over `split_mut` (one thread) or rayon `par_split_mut` (`par` variants) on a per-run mutable copy of the batch, timed as phase `copy`, because simd-json parses in place
- `cujson-node` and `cujson-node-par` walk the tape with `Node` navigation over `Document::lines()`, serially or with the lines collected and walked in rayon
- `cujson-visit` and `cujson-visit-par` walk the tape with `Document::visit`, or with `Document::visit_range` over `Document::split_lines(threads * 16)` ranges in rayon
- `cujson-pipe` (`run_pipeline` in `engines.rs`) runs `--gpu-threads` producer threads that parse batches and send each `Document` through a `sync_channel`, while the main thread walks the received documents with `visit_range` in rayon; it reports wall time with `parse busy` and `walk busy` (busy time summed over threads), is skipped at the `parse` level, and only overlaps when `--batch-mb` is below the corpus size
- Phases reported for cuJSON engines: `gpu parse` (one `parse_lines` call: host-to-device copy, kernels, tape copy back to pinned host memory) or `cpu tape build`, `walk`, and `free` (dropping the `Document`)

### Checksum gate

- `walk.rs` folds every node into a `u64`: a type tag, integer-or-float bits (`as_i64`, else `as_f64`; a simd-json `U64` above `i64::MAX` folds as `f64`), a hash of every unescaped key and string, array length and element order, and object entries combined by wrapping addition, because `simd_json` objects iterate in hash order
- `HashVisitor` in `walk.rs` computes the same value from `Visitor` events as `walk_cujson` does from `Node`s
- Before commit 6f08964 the gate compared each walk result only with earlier engines in the same `run` invocation, so a run with a single engine was unchecked; since 6f08964 the reference is a `simd-par` walk over every batch, computed at the start of every `run` that includes the `walk` level, and a mismatch aborts the run
- `walk.rs` has three unit tests: `parsers_agree_on_edge_cases` (simd-json against the CPU-reference tape on numbers, escapes, nesting and key order), `checksum_detects_differences` (value, key, array order and number type each change the checksum) and `visitor_checksum_matches_node_walk`
- simd-json 0.17 returns `InvalidNumber` for the integer `123456789012345678901234567890` (beyond `u64`), where the cuJSON walker folds such a number through `as_f64`; the committed file contains no such number

## Verification tiers

- Tier 1 (container, no GPU): `cargo fmt --all --check`, `cargo clippy --workspace --exclude cujson-py --all-targets -- -D warnings`, `cargo test --workspace --exclude cujson-py` and `cargo test -p cujson --features cpu-reference,serde` pass at 6f08964; `verify` on the committed file reports 1,818 rows and 0 mismatching checksums between simd-json and the CPU-reference tape
- Tier 2 (container, `CUJSON_CUDA_ARCHS=86`, `--features cuda`): clippy and the build pass at 6f08964; `run --engines cujson-visit-par` prints `unavailable (CUDA error 35 ...)` and exits without panicking on a host with no driver
- Tier 3 (RTX 3090, CUDA 13.2, host checkout): the `--include-ignored` tests of `crates/cujson/tests/gpu.rs` passed at 63a7ea2; `run` results at 5c2250b and de94433 include a `simd-par` row first, so their `cujson-*` checksums matched simd-json's; the `--gpu-threads 2` and `3` runs at 78bbcf0 and 8da77e4 ran `cujson-pipe` alone, before the gate reference existed, and their checksums were not compared; the second `--gpu-threads 1,2,3` run at 6f08964 (`cujson-pipe` alone) passed the simd-json reference check at every thread count; no Tier 3 test result (`--include-ignored`) has been reported for 5c2250b through 6f08964
- Not run anywhere: CUDA 12.x hosts, GPUs other than sm_86, the PTX fallback, the `cujson-py` GPU tests against a published wheel

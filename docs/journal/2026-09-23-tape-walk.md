# 2026-09-23: Single-pass tape walk (`Document::visit`)

Related entries: `2026-09-23-bench.md` (the benchmark that measured it), `2026-09-23-bench-measurements.md` (numbers), `2026-09-23-lane-b-tape-navigator.md` (the `Node` navigator this walk sits beside).

## Current State

### API

- `crates/cujson/src/tape/visit.rs` defines the `Visitor` trait: `begin_object`, `end_object`, `begin_array`, `end_array`, `key(&str)`, `string(&str)`, `number(&[u8])`, `boolean(bool)`, `null()`, all with empty default bodies; `key` and `string` receive unescaped text valid only for the duration of the call, `number` receives the raw unparsed bytes because cuJSON does not validate number grammar
- `Document::visit(&mut impl Visitor)` walks every value once in document order; for JSON Lines the top-level values arrive in line order with blank lines skipped
- `Document::split_lines(parts)` returns at most `parts` ranges of tape indices, each a whole number of top-level values, of similar entry counts; it hops from line to line through `pair_pos` at line openers (via `Document::top_level_delims` in `document.rs`), so it touches one tape entry per line
- `Document::visit_range(range, &mut impl Visitor)` walks the values of one `split_lines` range and returns `Error::IndexOutOfRange` for a range outside `1..len-1`
- The walk reads `structural` and the input sequentially and never reads `pair_pos`; the GPU tape defines `pair_pos` only at opener entries (`tape/FORMAT.md` §3)
- `Node` navigation (`Document::root`, `lines`, `Node::get`, `iter_object`, `as_str`) is unchanged and still checks every string for UTF-8 validity

### Algorithm

- For each tape entry in the range, the walk takes the bytes between the previous entry and the current one, trimmed of ASCII whitespace, as a span; an entry `:` makes the span a key, an entry `,`, `\n`, `}` or `]` makes a non-empty span a scalar value, and an entry `{` or `[` starts a container
- Empty containers (`[]`, `{}`) and `[null]` are told apart by span content, because their opener and closer are adjacent tape entries in both cases
- The span after the last entry, up to the end of the input, is a trailing scalar and is visited only by the range that ends at the last real entry
- A tape with no real entries (a top-level scalar document) is visited as one scalar

### UTF-8 handling

- `visit_range` runs `std::str::from_utf8` once over the input bytes from the start of the range's first span to the end of its last entry
- Each entry position must satisfy `prev <= pos < region_end`, otherwise the walk returns `Error::IndexOutOfRange`, so every span lies inside the validated region even for a hand-built tape passed to the public `Document::new`
- A key or string span is `"` + inner + `"`, so `inner` starts and ends next to an ASCII byte of a valid UTF-8 region and is itself valid UTF-8; the walk converts it with `std::str::from_utf8_unchecked`
- `unescape_into(bytes, out, validated)` takes a `validated` flag; the visitor passes `true` and `Node::as_str` passes `false`
- `crates/cujson/tests/visit_tests.rs` has `invalid_utf8_in_a_string_is_an_error` (a valid tape with one string's bytes replaced by `0xC3 0x28`) and `corrupt_tape_offsets_are_an_error_not_a_read_outside_the_region` (structural entries overwritten with 1 or 1000)
- The GPU shim validates the whole input as UTF-8 before returning a tape, and `build_tape_cpu` validates it as well, so a parsed `Document` never fails the region check

### Escape decoding

- `parse_hex4` in `document.rs` reads four hex digits through a 256-entry table (`HEX`) and rejects any non-hex byte, so a `\u` escape with a sign character such as `\u+123`, accepted before by `u32::from_str_radix`, returns `Error::InvalidEscape`
- `unescape_into` reserves the input length once and finds the end of each plain run with `position` for a backslash
- Before this work each `\uXXXX` went through `from_utf8` and `from_str_radix`, and `Node::as_str` allocated a `String` per escaped string

### Tests

- `crates/cujson/tests/visit_tests.rs` compares the `Visitor` event stream with `Node` navigation for standard-mode edge cases (`{}`, `[]`, `[null]`, `[[]]`, nested empties, escapes, pretty-printed input, top-level scalars), JSON Lines edge cases (blank lines, trailing newline missing, scalar lines), both fixtures, and for `split_lines` at 1, 2, 3, 7 and 64 parts

## Measurements (CPU-built tape of the committed file, 20 threads, container)

- Entry loop that sums `input[pos]`: 0.005 s; adding span trimming: 0.018 s; adding a backslash scan plus `from_utf8` on every key and string: 0.212 s (`contains` alone 0.100 s, `from_utf8` alone 0.158 s, `position` alone 0.081 s, `is_ascii` alone 0.104 s)
- Serial walk with a `Visitor` that ignores every value: 0.613 s before the unescape work, 0.476 s after the hex table, 0.375 s after tighter run scanning, 0.279 s after the once-per-range UTF-8 check
- Serial walk with `HashVisitor`: 0.716 s, then 0.552 s, 0.451 s, 0.332 s at the same stages
- `run --tape cpu` walk phase: `cujson-node` 0.793 s to 0.674 s (0.574 s after all changes), `cujson-visit` 0.524 s to 0.333 s, `cujson-visit-par` 0.050 s to 0.031 s, `cujson-node-par` 0.063 s
- The walk phase of `cujson-node` reads 0.755 s over a GPU-built tape and 0.788 s over the CPU-built tape before the unescape work
- On the RTX 3090 host the `walk` phase of `cujson-visit-par` reads 0.050 s before and 0.037 s after these changes
- A first version of `split_lines` scanned every tape entry serially and cost more than the `Node`-based parallel walk (`cujson-visit-par` walk 0.126 s against 0.063 s); hopping through `pair_pos` at line openers replaced it
